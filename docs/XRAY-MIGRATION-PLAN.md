# Переход на простую архитектуру VPN

Дата: 5 октября 2026 года. Статус: этап 1 начат на ветке codex/xray-beta.
Этот вариант заменяет предыдущий подробный план.

Реализован отдельный Go-процесс с libXray/Xray-core 26.9.30 и локальными
проверками транспорта/lifecycle. Go API используется напрямую: XCFramework
для отдельного процесса не нужен. Ручная проверка TUN ещё не выполнена;
инструкции и границы прототипа — в docs/XRAY-RUNTIME-CHECK.md.

## Минимальные требования

Сохраняем текущий UI, MetaCubeX/meta-rules-dat как источник маршрутизации,
HaGeZi Pro Mini как источник блокировки рекламы и пользовательские настройки.
Сохраняем полный/выборочный режимы, выбранные сервисы, доменные правила,
импорт подписки и выбор сервера. Правила процессов удаляем по согласованию;
их элементы UI снимаем, остальной интерфейс не переделываем.

Ruby-генератор, shell-контроллер, файловая очередь, нынешние классы, журнал
транзакций и способ хранения не являются требованиями. Их можно заменить.
Текущее решение не задаёт внутреннюю архитектуру нового.

Пользователь подтвердил отсутствие Apple Developer Program.
NetworkExtension не выбираем: не ставим разработку и запуск в зависимость
от Developer ID и provisioning для системного VPN.

## Выбранная архитектура

Три ответственности:

| Часть | Что делает |
| --- | --- |
| Приложение с текущим UI | Ввод, подписки, получение списков и отображение подтверждённого состояния |
| Компилятор политики | Из узлов, режима и списков получает согласованные настройки DNS/маршрутизации Xray |
| Нативный VPN-сервис | Принимает снимки настроек, управляет runtime и сетью, проверяет связь и восстанавливается |

Сервис работает под launchd. Он запускает отдельный процесс с libXray:
ядро может зависнуть, а сервис всё равно должен суметь завершить его
и восстановить сеть. Два процесса нужны для этой границы отказа, а не
для двух независимых систем восстановления. Один работающий VPN-движок.

Приложение отправляет фиксированные команды через приватный локальный IPC.
Для сборки без Developer ID достаточно контролируемого локального канала:
приватный Unix socket, проверка UID клиента и ограниченная схема сообщений.
Это доверие владельцу установки, не гарантия идентичности подписанного издателя.
Не добавляем XPC-инфраструктуру только ради названия технологии.

Сервис принимает настройки и проверенные данные, но не произвольные root-команды,
пути, исполняемые файлы или неконтролируемый Xray JSON из подписки.
Компилятор используется одним каноническим путём; привилегированная сторона
проверяет входы и допускаемые конфигурационные поля. Расширенные настройки
XHTTP проверяются отдельно, чтобы сохранять транспортную семантику.

Runtime и сервис устанавливаются в root-owned каталог. Их нельзя подменить
через пользовательский кэш. Первый install/update компонента требует
обычного администраторского разрешения macOS. Developer ID для выбранного
пути не нужен; это не отменяет пользовательские ограничения запуска
скачанного ad-hoc подписанного приложения.

## Одна конфигурация и один владелец

Сервис — единственный владелец принятой VPN-конфигурации и фактического
состояния. Приложение не сохраняет второй экземпляр desiredOn/activeNode
для управления runtime. Локальный draft UI не является принятой настройкой.
Обычные настройки оформления могут оставаться в UserDefaults.

Принятый снимок включает узлы, выбранный пользователем сервер, режим,
переключатели, правила и версии списков. Фактически выбранный при recovery
узел — runtime-данные, отличные от предпочтения пользователя.
UI отображает фактический узел и причину переключения.

Изменение сначала готовится и проверяется в изолированном процессе,
затем применяется одной последовательной очередью сервиса.
Предыдущий снимок хранится до успеха; ошибка оставляет его доступным для отката.
Новая конфигурация и её правила образуют одну версию с общим хэшем.

Простой механизм хранения: приватные неизменяемые снимки и атомарная смена
принятого указателя. До реализации проверяем поведение при аварии между
сохранением, запуском и принятием: после перезапуска получается однозначный
принятый снимок, без второй схемы commit в приложении.
Потерянный ответ разрешается чтением ID принятого снимка.
Сохранение проверенных настроек и наличие Интернета не смешиваем.

Старый ConfigurationCoordinator можно удалить после переноса ответственности
в сервис. Сохраняем полезное свойство атомарности, а не существующий механизм.

## Правила и блокировка

MetaCubeX остаётся источником, формат .srs сохранять не требуется.
Начинаем с JSON тех же наборов в ветке sing и преобразования используемых
условий в Xray. Существование JSON YouTube проверено; наличие и эквивалентность
остальных наборов подтверждает прототип.

Сохраняем 13 категорий: youtube, telegram, whatsapp, instagram, facebook,
twitter, discord, openai, anthropic, google-gemini, cursor, github-copilot,
spotify. Также IP-наборы Telegram, Facebook и Twitter.

Неизвестные условия источника не игнорируем. Если JSON слишком велик,
используем компактные локальные geodata после проверки эквивалентности.
Универсальный конвертер всех форматов sing-box не нужен.

HaGeZi Pro Mini остаётся доменным блокировщиком в DNS и правилах трафика.
Один компилятор владеет нормализацией и приоритетами для обоих путей.
Для обычных публичных назначений block выше vpn/direct.
LAN, VPN-uplink, bootstrap DNS и необходимые служебные направления имеют
явные исключения. В selective невыбранное идёт direct, выбранные домены/IP — VPN;
в all публичный трафик — VPN. Ошибка VPN не включает скрытый direct-fallback.

Подключение не ждёт GitHub: в поставке есть встроенные данные обоих источников,
затем используется последний проверенный снимок.
Обновления идут отдельно, с пределами времени, байтов и числа записей.
Повреждённая загрузка или неудачное применение сохраняет действующие правила.
Одинаковый список не перезапускает ядро. DNS и маршрутизация не получают
разные версии одного обновления.

Первый вариант загружает обновления при работающем приложении:
MetaCubeX раз в сутки, HaGeZi раз в восемь часов.
С закрытым UI VPN продолжает работать на принятом снимке.
Отдельный автономный загрузчик добавляем только при необходимости.
Статус обновления берём из результата загрузки/применения, не из INFO-лога Xray.

## Надёжность без дополнительных настроек

- Один владелец connect/disconnect/recovery. Выключение отменяет восстановление;
  результаты прежней операции не могут включить VPN вновь.
- «Подключён» требует свежей успешной HTTPS-проверки через настоящий TUN-путь.
  Живой процесс, DNS-кэш и локальный SYN-ACK этого не заменяют.
- Проверки ограничены временем, выполняются сервисом отдельно от UI-таймера.
  Различаем отказ узла, отсутствие сети и отказ проверочного сайта.
- Перезапуски и переключения ограничены. Offline не вызывает перебор узлов.
  Пробы кандидатов и валидация не изменяют глобальное состояние работающего ядра.
- Состояния соответствуют текущему UI: выключен, подключается, подключён,
  восстанавливается/ждёт сеть, ошибка. Новые экраны не нужны.
- Настройки и секреты приватны: каталоги 0700, файлы 0600, нет credentials в argv,
  обычных ошибках или публичных логах. Журналы ограничены по размеру.
- VPN продолжает работать без UI. Повторное открытие читает действующее состояние.
- LAN и VPN-сервер остаются direct; bootstrap не использует подменённый resolver.

Сервис сохраняет исходные сетевые настройки до изменения.
После off, неудачного запуска, аварии runtime, restart сервиса и uninstall
он восстанавливает DNS/маршруты и удаляет только принадлежащие нам изменения.
Если сервис упал, launchd поднимает его; аварийный журнал позволяет сначала
очистить осиротевший runtime и сеть. Работа со сменой Wi-Fi и sleep/wake
опирается на сетевые события, а не на задержку shell-цикла.

## Порядок реализации

| Этап | Результат |
| --- | --- |
| 1. Рабочий прототип | Закреплённая сборка libXray для macOS; TUN, uplink, DNS и все используемые VLESS-транспорты; проверенное восстановление доменов |
| 2. Компилятор политики | MetaCubeX, HaGeZi и пользовательские домены; full/selective, IP-наборы, встроенные данные и проверенный кэш |
| 3. Нативный сервис | Один снимок настроек, локальный IPC, запуск/остановка runtime, восстановление системной сети |
| 4. Health и recovery | Проверка настоящего трафика, ограниченные попытки, отмена, фактический узел и состояние |
| 5. Подключение UI | Замена внутренних вызовов без редизайна; однократный перенос подписок и настроек |
| 6. Приёмка и удаление старого | Проверки отказов и реального Mac; удалить старый shell/Ruby/SOCKS-путь и ненужные зависимости |

Миграция сначала останавливает старый VPN и восстанавливает сеть.
После этого устанавливает и запускает новый сервис.
При неудаче доступен откат установки и приватная резервная копия настроек.
Два владельца TUN/DNS одновременно не работают.
Совместимость служит только миграции и удаляется после приёмки.

sing-box не включаем в базовую архитектуру. Резерв оправдан конкретной
используемой конфигурацией, которую Xray не поддерживает, а не timeout сервера.
Пока такого случая нет, второй стек не реализуем.

## Существенные нюансы

1. **Без Apple Developer сеть остаётся нашей ответственностью.**
   Нативный сервис убирает shell-оркестрацию, но восстановление DNS и маршрутов
   всё равно нужно реализовать и проверить. В этом пути остаётся установка
   компонента с администраторским разрешением.
2. **Доменная маршрутизация на TUN.** Ядро получает IP-пакеты.
   Одного TLS-sniffing недостаточно для сохранения смысла доменных правил.
   Проверяем DNS/FakeDNS и UDP/QUIC до массового переписывания.
   FakeDNS может оставлять синтетические адреса в кэше; это отдельный тест
   остановки, перезапуска, исчерпания пула и сочетания с IP-наборами.
3. **libXray — API к ядру, не готовый VPN-клиент.**
   Версии фиксируем: API не обещает стабильность.
   В одном процессе один Go runtime; testXray/pingBatch не выполняются рядом
   с действующим managed core. Большие списки учитывают предел Invoke.
4. **Блокировка остаётся доменной.** Она не удаляет рекламу внутри общего
   домена контента. Собственный шифрованный DNS приложений ограничивает
   видимость имени. Не добавляем для обхода этого MITM или второй сетевой фильтр.
5. **IPv6 выбираем заново.** Старое глобальное отключение не является требованием.
   Реализуем корректный IPv6-туннель либо явную ограниченную политику;
   скрытый обход VPN через IPv6 недопустим.
6. **Изоляция отказов требует отдельного процесса ядра.**
   Таймаут задачи не прерывает зависший нативный вызов libXray.
   Надзор сервиса обеспечивает ограниченную остановку и cleanup.

## Критерий готовности

Автотесты с fake runtime/сетью и управляемым временем не меняют сеть хоста.
Ключевые проверки: ядро живо, трафик не идёт; DNS-кэш; offline; падение/зависание;
off во время recovery; потерянный ответ применения; сбой сохранения; сломанный
список; все категории доменов/IP; блокировка пересекается с VPN-пресетом;
LAN/uplink; закрытый UI; авария сервиса; однократная миграция и откат.

На отдельном Mac: реальные серверы и транспорты, sleep/wake, смена сети,
offline→online, DNS/IPv6 после остановки, доменные правила, HaGeZi и миграция.
Проверяем расход памяти, число процессов и ограниченность журналов.
Сборка и fake-тесты эту приёмку не заменяют.

Узкие регрессии добавляем по мере реализации, затем ./Scripts/validate.sh.
Новые сервис и runtime входят в validation.
docs/ARCHITECTURE.md обновляется по фактически реализованной архитектуре.
Релиз и публикация отдельно от подготовки этого плана.
