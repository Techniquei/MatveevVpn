## Что пользователь уже решил

- Сохраняем текущий интерфейс, импорт подписки, выбор сервера, пользовательские
  настройки, полный и выборочный режимы, сервисные пресеты и доменные правила.
- Источник маршрутизации — `MetaCubeX/meta-rules-dat`, блокировка рекламы —
  `HaGeZi Pro Mini`. Сохраняем их смысл и данные, не обязательно нынешний формат
  `.srs` или способ применения.
- Правила приложений, процессов и executable-path можно удалить. Остальной UI
  не переделываем ради смены двигателя.
- Основной двигатель — **XTLS/libXray с Xray-core**. Это не научная библиотека
  `xraylib`. Нынешняя реализация использует прямой Go API, без XCFramework.
- Apple Developer Program отсутствует. Системный VPN через NetworkExtension
  в этот план не входит. Установка привилегированного компонента всё равно
  требует обычного разрешения администратора macOS.
- Ruby-генератор, shell-контроллер, файловую очередь, классы координатора и
  хранение можно заменить. Старые внутренние границы в `AGENTS.md` описывают
  действующую архитектуру, а не запрет на согласованную пользователем замену.
  Атомарность, сериализация, приватность и восстановление сети обязательны.
- sing-box остаётся возможным резервом для **конкретной используемой
  конфигурации, несовместимой с Xray**. Пока такой случай не доказан, второй
  backend не реализуем. Timeout не повод автоматически менять двигатель.

Полный импорт произвольного sing-box JSON и универсальный конвертер `.srs`
не обещаны. Форматы списков и протоколы узлов — разные вопросы совместимости.
Нельзя молча потерять неизвестное условие списка или транспортный параметр.

## Целевая ответственность

```text
текущий UI → приватный локальный IPC → нативный сервис под launchd
                                      ├─ принятый снимок / сеть / health / recovery
                                      └─ отдельный процесс libXray
```

Сервис — один владелец принятой VPN-конфигурации и восстановления. Отдельный
процесс ядра нужен, чтобы зависший вызов libXray можно было завершить, сохранив
работоспособный сервис для cleanup. Два VPN-стека одновременно не запускаются.
Сервис и компилятор — Go в существующем модуле; Swift остаётся UI/IPC клиентом.

UI отправляет намерения и показывает подтверждённое состояние. Draft и
настройки оформления могут оставаться в приложении; второй управляющий
`desiredOn`/`activeNode` рядом с состоянием сервиса не нужен. Предпочтительный
сервер пользователя отличается от фактического узла, выбранного recovery.

Один канонический компилятор формирует DNS и маршруты из одного снимка правил.
Сервис допускает только проверенные поля и фиксированные команды. Приватный
Unix socket с проверкой UID — доверие владельцу установки, не криптографическая
идентичность издателя. Runtime и сервис должны быть root-owned; запуск бинарника
из изменяемого пользовательского кэша как root недопустим. Точные IPC/revision,
commit и сетевые контракты находятся в `XRAY-DECISIONS.md`.

Принятый неизменяемый снимок объединяет узлы, предпочтение сервера, режим,
правила и версии списков с общим хэшем. Атомарная смена указателя, предыдущий
снимок и однозначное восстановление после сбоя заменяют распределённый commit.
Apply принимает валидные настройки durable до runtime reconciliation;
activation error очищает сеть, сохраняет настройки и показывает ошибку.
Явный rollback — новый Apply предыдущего снимка, не следствие HTTP timeout.
Потерянный ответ разрешается чтением ID принятого снимка. Сохранённая настройка
и доступность Интернета — разные состояния.

Go — `1.27.1`, libXray — `v1.260930.0`, Xray-core сообщает `26.9.30`.
Точная версия Xray-core закреплена в `go.mod/go.sum`. Сборка пока только
**macOS arm64**. Intel/universal не реализованы. Загрузки и бинарники в `.build/`
игнорируются Git; существующие release artifacts не изменены.

Важные пределы прототипа:

- Вход — newline JSON, максимум **1 MiB**, envelope version `1`, фиксированные
  действия и коды ошибок. Это собственный протокол; лимит upstream `Invoke`
  здесь неприменим, потому что используется прямой Go API.
- `running` означает состояние ядра, **не работающий VPN**.
- Worker принимает Xray JSON от доверенного родителя, включая потенциально
  опасные при root-запуске поля/пути/environment. Он **не готовый публичный
  privileged API**. Не подключать его напрямую к root socket или launchd.
- Валидация меняет глобальное состояние процесса libXray. Делать её и пробы
  кандидатов в отдельных одноразовых worker; не переиспользовать валидатор
  как действующее ядро. Защита от validate рядом с живым core уже есть.
- Обычные команды не имеют собственных дедлайнов. Будущий supervisor обязан
  ограничивать ожидание и завершать зависший дочерний процесс. При EOF/signal
  shutdown ограничен пятью секундами.
- Engine logs сейчас отключены. Дальше нужны ограниченные приватные
  диагностические журналы, которые не засоряют JSON stdout и не блокируют core.

На `4408a0f` прошли `bash Scripts/test-xray-runtime.sh` и полная validation.
Доказаны loopback HTTP, освобождение listener, строгие сообщения и завершение
процесса. RAW/TLS/WS/gRPC/REALITY/XHTTP TLS/REALITY прошли **конструирование
конфигураций**; реальный handshake и трафик на этих транспортах ещё не доказаны.

## Порядок дальнейшей работы

### 0. Восстановить контекст без изменения сети

Проверь ветку, commit, `git status`; прочитай документы и существующий путь
от UI до `ConfigurationCoordinator`, `SystemService`, `build-config.rb` и
`controller.sh`. Для каждой меняемой обязанности укажи её нового владельца.
Не лечи старую модель дополнительным recovery в UI. Исходная жалоба:
живой процесс/успешный ответ DNS из кэша могут показывать «включён», когда
полезный трафик не проходит. Причина всех сбоев не доказана как баг sing-box;
наличие Kaspersky в диагностике также не доказывает его вину.

### 1. Закрыть технические риски runtime до массовой миграции

Первое действие с пользователем — ручная TUN-проба. После сборки попроси
выключить текущий VPN и выполнить в Terminal:

```sh
sudo /Users/vladimir/Documents/matveevVpn/.build/xray-runtime/matveev-xray-runtime --tun-smoke
```

Успех: одна JSON-строка, `created: true`, `released: true`, без `error`, обычный
Интернет после пробы работает. Она создаёт временный utun900–999 с link-local
адресом, не меняет системный DNS/default route и не доказывает работу VPN.
Пароль вводится в Terminal. Попроси только результат и состояние Интернета,
не подписку или приватную конфигурацию. Timeout без результата — не успех.

Затем отдельным минимальным стендом проверь настоящий TUN-трафик, DNS,
uplink вне туннеля и используемые серверные транспорты. Перед каждым реальным
тестом дай способ остановки и отката. Автотесты используют fake-сеть.

**Главный gate:** доказать сохранение доменных правил для TCP и UDP/QUIC.
TUN получает IP; одного sniffing недостаточно. Реализуй выбранный persistent
FakeDNS по `XRAY-DECISIONS.md`, проверь остановку, рестарт, старые DNS-кэши,
исчерпание пула и пересечение с IP-наборами. Не объявляй этап завершённым
по одному utun smoke.

### 2. Реализовать один компилятор политики

Подтверди наличие и семантическую эквивалентность JSON из ветки `sing`
MetaCubeX для всех 13 категорий: youtube, telegram, whatsapp, instagram,
facebook, twitter, discord, openai, anthropic, google-gemini, cursor,
github-copilot, spotify; отдельно IP-наборов Telegram/Facebook/Twitter.
Пока проверено только наличие YouTube JSON.

Переводи используемые условия источника в Xray с сохранением логики
AND/OR, exact/suffix/keyword/regex и CIDR там, где они встречаются. Неизвестное
условие отклоняет обновление целиком. Не делай универсальный конвертер.
Реальные небольшие обезличенные fixtures должны доказывать эквивалентность.

HaGeZi и пользовательские правила проходят тот же канонический путь.
Для публичных назначений block имеет приоритет над vpn/direct; служебные
исключения, LAN и uplink явные. Selective final — direct, full final — VPN.
Сбой VPN не включает скрытый direct fallback.

Поставляй встроенные списки и последний проверенный кэш. Обновление ограничено
временем/размером/числом записей, не блокирует connect, атомарно меняет DNS и
маршруты; ошибка сохраняет старый снимок, одинаковые данные не рестартуют core.
В первом варианте обновляет приложение: MetaCubeX раз в сутки, HaGeZi раз в
восемь часов; закрытый UI оставляет действующие данные. Проверь полный размер
политики против лимита 1 MiB, память и startup; компактные geodata допустимы
после доказательства семантики, простое бесконечное увеличение лимита не нужно.

### 3. Сделать нативный сервис и безопасную транзакцию

Реализуй ограниченный IPC, проверку клиента/UID, допуск конфигурации, root-owned
установку и надзор за worker. Сериализуй connect/off/apply/recovery одной
очередью. Валидация — отдельный процесс, дедлайны не продлеваются очередью.
Off и смена поколения отменяют старые результаты, чтобы VPN не воскресал.

Перенеси принятое состояние в сервис и реализуй приватные снимки/откат.
Проверь сбой сохранения, потерянный ответ, аварии между записью/запуском/commit,
повторный запрос и запуск сервиса после сбоя. Принятие настроек не требует
доступности внешнего Интернета; не теряй подписку из-за offline.

### 4. Сделать управление сетью восстанавливаемым

До изменения DNS/маршрутов сохраняй аварийный журнал. Сервис владеет только
своими изменениями и учитывает физический интерфейс/сетевую службу. Сохрани
direct для LAN/private/mesh и сервера; bootstrap resolver/uplink не должны
читать уже подменённый системный DNS или входить в TUN по кругу.

После off, частичного старта, crash/hang core, restart сервиса и uninstall
восстанавливай сеть; launchd поднимает сервис, который сначала согласует
осиротевшие процессы и журнал. Не затирай посторонние изменения сети старым
снимком. Проверь смену Wi-Fi и sleep/wake через сетевые события. Реализуй
IPv6-политику из контракта: public IPv6 блокируется, private/link-local
сохраняется, глобального отключения нет. При невозможности обеспечить политику
старт отклоняется, скрытый bypass не допускается.

### 5. Заменить health и recovery одним владельцем

Состояние «подключён» требует свежего успешного HTTPS-запроса через фактический
TUN, не просто SOCKS, DNS или TCP SYN. Предусмотри независимые проверочные
назначения, чтобы отказ одного сайта не означал отказ VPN.

Различай offline/отказ узла/отказ проверки. Пределы и интервалы уже заданы
в `XRAY-DECISIONS.md`. Перезапуски и failover ограничены,
offline не перебирает серверы, off отменяет recovery. Пробы альтернативных
узлов не трогают работающий core. С закрытым UI сервис продолжает работать;
двухсекундный UI timer только читает состояние, не запускает сетевые работы.

Обязательная регрессия исходной жалобы: core жив, DNS отвечает из кэша,
HTTPS через TUN не проходит — UI не остаётся «подключён».

### 6. Подключить текущий UI и мигрировать настройки

Заменяй внутренние вызовы без редизайна. Показывай подтверждённое состояние,
фактический recovery-узел и причину переключения. Удали согласованные элементы
маршрутизации процессов. Перенеси подписки/настройки один раз со стабильными
идентичностями и приватной резервной копией.

Сначала останови старый VPN и восстанови сеть, затем запускай новый сервис.
Сбой установки должен оставлять понятный откат. Старый координатор можно
удалить после переноса атомарности, старые controller/Ruby/sidecar — после
замены обязанностей и приёмки. Временные ветви миграции имеют условие удаления;
не оставляй два владельца состояния или два TUN ради совместимости.

### 7. Принять рабочую бету и подготовить релиз

После каждого изменения — узкие регрессии, после законченного этапа кода —
`./Scripts/validate.sh`. Новые сервис/компилятор включаются в общий validation.
Fake-тесты не меняют реальные DNS, маршруты, launchd или VPN хоста.

Реальную приёмку попроси у пользователя: full/selective, все категории и
IP-наборы, пересечение HaGeZi с VPN-пресетом, LAN/server direct, реальные
транспорты, IPv6/DNS после off, crash/hang, offline→online, sleep/wake,
смена сети, закрытый UI, install/update/uninstall и откат миграции.
Проверь память, число процессов, startup/cleanup и ограниченность журналов.

Только для прошедшей приёмку сборки приложения выбери новый номер беты,
подготовь DMG и проверь существующий Sparkle/GitHub release workflow.
App version, IPC/controller contract и schema version меняются независимо
по фактической несовместимости. Проверь обнаружение беты через существующий
channel/appcast и отсутствие преждевременного обновления компонента.
Прототип worker не публикуется как завершённый переход.

## Не потерять при следующей остановке

Основная передача Grok — fixtures/компилятор по утверждённой политике, Swift IPC
и UI wiring, упаковка, проверки и документация. Core/service/DNS cleanup ещё
нужно реализовать: это существенная работа даже при готовых решениях.
Если передача происходит сейчас, не называть остаток только лёгкой доработкой.

В отчёте каждого этапа оставляй commit, что изменено, какие команды действительно
прошли, что ещё не проверено на Mac и ровно следующий шаг. Обновляй архитектуру
по реализованному состоянию. Не записывай credentials, приватные конфиги,
подписки, логи, скачанные бинарники или build output в Git. Приватные каталоги
