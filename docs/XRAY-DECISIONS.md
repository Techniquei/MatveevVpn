# Зафиксированные решения для новой беты

5 октября 2026 года. Этот документ уточняет `XRAY-MIGRATION-PLAN.md`.
При расхождении описания руководствоваться решениями ниже и `ARCHITECTURE.md`.

## 1. Два Go-процесса, один владелец

Сервис и компилятор пишем на Go в существующем модуле `Runtime`.
Swift остаётся UI и клиентом. Сервис под launchd владеет состоянием, DNS,
маршрутами, health/recovery и дочерним core worker. Worker владеет только
Xray instance/TUN. Никаких отдельного shell watchdog и восстановления в UI.

Используем закреплённый Xray, без XCFramework и Go runtime внутри Swift.
Поставка первой беты — macOS arm64, как текущий build. Второй VPN backend
не включаем, пока конкретная используемая конфигурация не доказала его нужду.

## 2. Настройки принимаются независимо от Интернета

Принятая запись:
`{schema, revision, snapshotID, desiredOn, lastRequestID, lastRequestPayloadHash}`.
Snapshot — неизменяемая полная конфигурация пользователя и версии списков,
ID — хэш канонических байтов. Фактический узел и health — runtime-состояние.

`Apply`: проверить вход → скомпилировать → проверить одноразовым worker →
записать snapshot с fsync → атомарно заменить accepted record с fsync
каталога → reconciliate runtime. До commit ошибка сохраняет старую запись.
После commit ответ различает `acceptedRevision` и `runtimeState`.
Перед заменой active policy приостанавливаем публичные DNS-ответы (SERVFAIL),
останавливаем прежний core, запускаем новый и открываем DNS только для его
revision. `activeRevision` — фактические runtime metadata, не второй accepted
record. Новая DNS-политика не обслуживает старую маршрутную конфигурацию.

Отказ Интернета не откатывает подписку. При offline сохраняем полный snapshot
и desiredOn, состояние `waiting-network`; второй disabled snapshot не нужен.
При локальном activation failure останавливаем core, восстанавливаем сеть,
показываем ошибку и сохраняем принятую настройку. Предыдущий snapshot остаётся
для явного rollback через тот же Apply. Скрытого переключения на старую
политику после принятия новой нет. Откат установки бинарников — отдельный
фиксированный путь установщика, не второй commit пользовательских настроек.

Это уточнение семантики: атомарность гарантируется для принятой конфигурации;
connected гарантируется отдельной свежей проверкой. Не обещать атомарную
непрерывность внешней связи при замене core.

## 3. IPC с ревизией, off не ждёт зависший apply

Unix socket в root-owned каталоге 0711; socket 0600, доступ только UID владельца
установки, peer UID проверяется через системный API. Фиксированные команды:
`GetStatus`, `Apply`, `SetDesiredOn`, `ProbeNodes`. Установка/удаление выполняются
фиксированным установщиком с администраторским разрешением, не произвольным IPC.

Envelope: `version`, `requestID`, `action`, `expectedRevision`, типизированный
payload. Неизвестные поля отклоняем. Начальный предел сообщения — 1 MiB,
таймаут чтения — 5 секунд. Подписки, узлы и данные списков передаются в payload;
caller-supplied Xray JSON, пути, environment и команды запрещены.
Полные списки разбиваем на ограниченные типизированные порции с одним upload ID,
общим лимитом и хэшем; неполная загрузка не становится принятой конфигурацией.
Это staging транзакции, не второй источник настроек.

Мутации требуют expectedRevision. Повтор последнего requestID с тем же payload
возвращает прежнюю acceptedRevision и текущий runtime state; повтор с иным
payload отклоняется. Старый request
с устаревшей ревизией получает conflict. После потерянного ответа UI читает
GetStatus и принятую ревизию, не повторяет root-операцию вслепую.

Один event loop принимает решения; долгие процессы/загрузка не блокируют его.
Off сначала durable сохраняет desiredOn=false, отменяет generation и pending
apply/probes, затем останавливает core и очищает сеть. Результат apply перед
commit снова проверяет revision/generation. Off не стоит за зависшим core.
Каждая операция имеет общий deadline; TERM grace 5 секунд, затем KILL.
При ошибке сохранения off отмена/stop/cleanup всё равно выполняются,
session recovery запрещается, UI получает ошибку persistence. После сбоя диска
durable off не гарантируется; не отвечать успехом сохранения.

## 4. Доменная маршрутизация — FakeDNS с устойчивой таблицей

Выбираем FakeDNS, потому что имя необходимо также для UDP/QUIC и зашифрованного
ClientHello. Sniffing — дополнительный источник имени, не основа политики.

**Таблица принадлежит DNS-части Go-сервиса, переживает рестарт core.**
Сервис отвечает TCP/UDP DNS на loopback; системный DNS физической службы
указывает на этот endpoint. При запросе публичного имени:

1. Проверить блокировку; заблокированный домен получает NXDOMAIN.
2. Выдать стабильный fake IPv4 из `198.18.0.0/15`.
3. Новую пару durable сохранить **до** ответа клиенту.

LAN/`.local`/локальные DNS-зоны и bootstrap получают реальные адреса через
сохранённый исходный resolver, с привязкой к физическому интерфейсу. Публичные
неадресные DNS-запросы обрабатываем через выбранный real upstream; не выдаём
синтетические адреса для них. Для HTTPS/SVCB удаляем address hints, чтобы они
не обходили FakeDNS; незнакомый вариант отклоняем безопасным DNS-ответом.

Хранилище таблицы — приватный append journal с длиной/контрольной суммой записи;
при старте читается только подтверждённый целый префикс. Индексы в памяти —
производный кэш. Не переиспользовать fake IP для другого домена, даже после off.
Повреждённый/неполный хвост не удаляем автоматически: он мог содержать уже
выданные пары. При повреждении allocation останавливается с table-error до
проверенного восстановления; известный целый префикс пригоден для lookup,
неизвестные synthetic IP блокируются. Не начинать allocation с длины префикса.
Лимит первой беты: 65 536 доменов и 64 MiB journal; переполнение — SERVFAIL и
диагностическая ошибка, без молчаливой подмены или real-IP fallback.
Пул проверяется на конфликт с существующей сетью до старта.
Проверка повторяется при каждом сетевом reconcile, как и проверка обхода
IPv6-политики конкурирующими маршрутами. Новый конфликт останавливает runtime
с cleanup и понятной ошибкой.

Worker получает reverse lookup из этой же таблицы: immutable private mapping
записи публикуются перед DNS-ответом; отсутствующее соответствие блокируется.
Lookup-кэш worker инвалидируется по поколению таблицы и не считается настройкой.
У DNS-таблицы один writer — сервис. Производные записи можно восстановить из
journal; это не две независимо принимаемые версии DNS-политики.
Перед DNS-ответом запись должна быть видима worker: on-demand чтение актуальной
атомарно опубликованной записи, без negative lookup cache. При сбое публикации
ответ — SERVFAIL, даже если journal уже сохранил пару.

Встроенный FakeDNS Xray использует память/LRU и не даёт нужный контракт сохранения.
Поэтому reverse lookup реализуем как небольшой `dns.FakeDNSEngineRev0` в worker.
Для доступа к instance заменяем его lifecycle-вызовы на публичные API
закреплённого Xray-core (`LoadConfig`, `New`, `AddFeature`, `Start`, `Close`),
сохраняя отдельный процесс и текущую IPC-границу. Не форкаем ядро и не лезем
в private переменные libXray. Это допустимое уточнение выбора libXray: используем
его зависимости/полезные API, но не ограничиваем DNS приватным RunXray wrapper.
Если после замены lifecycle реально используемых API libXray не останется,
удалить его прямую зависимость: целевой worker тогда использует Xray-core
напрямую. Не сохранять библиотеку ради названия. Это решение будущей реализации;
текущий прототип всё ещё использует libXray.

Не включать builtin `fakeDns` и DNS server `fakedns` в core JSON вместе с нашим
holder. DNS upstream ядра возвращает реальные адреса. Holder добавляется до
Start; metadata sniffing восстанавливает имя до routing. Первым узким тестом
проверить lifecycle holder/dispatcher и стабильный TCP+UDP lookup после убийства
worker. Валидация использует тот же сборщик instance с временной fake-таблицей.
`Type()` holder возвращает `(*dns.FakeDNSEngine)(nil)`. При AddFeature/Start failure
обязательно Close; после закрытия создаём новый instance. Worker сам владеет
instance и active guard: `libXray.GetXrayState`/его guard не видят core, созданный
напрямую. Старые lifecycle/status вызовы удаляются вместе с заменой, регистрация
`main/distro/all` сохраняется. Metadata sniffing использует только `fakedns`
override для synthetic destination, не пытается угадать неизвестную пару по SNI.

На off удаляем маршруты пула и наш resolver override, flush системного DNS
ограниченной фиксированной командой. Приложение с собственным устаревшим
fake-IP кэшем может требовать повторного DNS запроса/перезапуска; это проверяем
на Mac и сообщаем как ограничение, не обещаем очистку чужих кэшей.

## 5. Сеть — сервис; public IPv6 в первой бете блокируется

Core autoroutes/system DNS выключены. Сервис устанавливает IPv4/IPv6 split
default routes через utun и отдельный маршрут fake-пула. Существующие LAN/mesh
маршруты сохраняются; явные direct исключения берутся из фактической сети.
Public IPv6, попавший в TUN, блокируется, public AAAA DNS получает пустой ответ.
Private/link-local IPv6 сохраняется. Системное глобальное отключение IPv6
не используем. При обнаруженном конкурирующем VPN/публичном more-specific route,
который обходит нашу IPv6-политику, старт отклоняем с понятной ошибкой.
IPv6 VPN-egress — отдельное последующее улучшение, не hidden bypass.

Все core direct/uplink сокеты привязаны к физическому интерфейсу (`sockopt.interface`),
сервер до изменения DNS разрешён независимым bootstrap resolver. Его адреса
имеют direct host routes. Привязка к интерфейсу не перекрывает unscoped
`0/1` и `128/1`, поэтому сервис ставит те же префиксы с `-ifscope` через
физический шлюз. Их видят только сокеты, привязанные к этому интерфейсу;
остальной трафик остаётся в utun. Реальный public DNS для VPN-доменов идёт через VPN;
для direct-доменов — physical-bound direct DoH. Числовой bootstrap + проверенный
TLS serverName исключают circular lookup. Не использовать системный resolver
для bootstrap после подмены DNS.

Сетевой адаптер Go использует фиксированные macOS executables с массивом argv
и ограниченным временем, без `sh -c`: networksetup/scutil/route и cache flush.
Их выполнение — одна внешняя граница с fake executables в тестах. На старте
сначала journal/reconcile, затем accepted desired state. AF_ROUTE события
запускают coalesced reconcile; перед health повторно читаем physical route,
чтобы смена сети/пробуждение не оставляли старую привязку.

До каждого изменения durable записываем прежнее/наше значение и identity
сетевой службы. Cleanup сравнивает текущие значения с установленными нами:
чужое новое значение не затирается старым. Частичный старт и crash очищаются
тем же путём. Orphan process проверяется по executable/start identity, не PID.

## 6. Одна политика, готовые приоритеты

В служебном DNS-пути перехват предшествует обычной маршрутизации. Для остального:
system/LAN/uplink исключения → HaGeZi block → явный пользовательский домен
→ выбранные MetaCubeX домены/IP → final режима. Для публичных назначений
block выше user VPN/direct. Пользовательский домен имеет приоритет над пресетом.
Домен из FakeDNS восстановлен **до** IP-проверки; fake IP не считается реальным
public/private destination. При необходимости IP-presets проверяем по real
resolution с выбранным DNS-путём, не по синтетическому адресу.
До LAN/private исключений стоит guard: оставшийся synthetic destination → block.
Маршрут `198.18.0.0/15` направлен в TUN даже при классификации пула как private.
Обработанный FakeDNS destination уже заменён доменом; неизвестный fake IP
никогда не отправляется наружу.
Public IPv6 guard идёт после LAN/uplink исключений, до публичных доменных правил.

Встроенные и скачанные данные нормализуются одним компилятором.
Неподдержанный оператор отклоняет весь новый список. Обновления UI: MetaCubeX
24 часа, HaGeZi 8 часов; closed UI использует последний snapshot. Компактные
geodata генерирует сервис из проверенных данных, если expanded JSON не помещается
в ограниченный worker message; пути назначает сервис, не пользователь.

## 7. Health и recovery с определёнными пределами

Свежий HTTPS через **реальный TUN** — условие connected; локальный SOCKS и SYN
не подходят. В selective служебные назначения проверки принудительно идут VPN.
Каждая проверка использует новое соединение, nonce/no-cache, TLS verification
и ограниченный ответ. Два независимых HTTPS endpoint; успех одного достаточен.
Проверочный трафик Go-клиента не привязывается к physical bypass.

При старте проверка сразу; в connected каждые 15 секунд, общий бюджет 6 секунд
на пару endpoints. Первая полная неудача снимает connected и запускает проверку
physical connectivity; три подряд при исправной physical сети запускают recovery.
Offline — waiting-network, без перебора серверов. Один restart текущего узла,
затем не более двух альтернатив; не более трёх switch за 10 минут. Exhausted
cycle — error и ожидание 30 секунд/сетевого события; off немедленно отменяет.
Status содержит время последнего успеха; после 30 секунд без свежего успеха UI
не показывает connected, даже если IPC не ответил. Fatal DNS/table error также
снимает connected. UI timer не делает network probes.

## 8. Установка и миграция

Фиксированный установщик копирует проверенный bundled пакет в root-owned
versioned directory, хранит owner UID и hashes в manifest. Старый VPN сначала
останавливается с восстановлением сети. Новый daemon впервые запускается off,
успех установки — локальный GetStatus, не доступность Интернета.
Ошибка локального старта откатывает пакет. Миграция настроек выполняет один
Apply, резервная копия приватна. Второй daemon/TUN не работает параллельно.
